# 编写计划

将开发需求和相关仓库上下文转化为可独立使用的可执行计划，为后续执行与决策提供清晰依据。

本 skill 负责编写计划，以及按下述条件维护与本次计划相关的架构决策记录（ADR）；不开始代码实现，不执行代码审查、系统验证、提交或其他交付操作。

## 收集上下文

编写计划前：

1. 只读取理解本次变更所需的代码、测试、配置、需求、设计与已确认讨论结论；根据项目 `AGENTS.md` 等入口，查阅适用的文档维护规则和相关 ADR。
2. 识别现有模式、受影响的职责以及兼容性约束。
3. 仅澄清那些会实质改变范围、行为或技术方向的歧义。

除非用户明确要求，否则不强制创建独立的需求探索文档、spec 或设计产物。ADR 的创建与维护遵循下述条件。

## 计划契约

每份计划通过正文或明确引用提供以下内容，复用已有需求、合同、设计和 ADR。

### 目标

描述完成后用户或系统能够观察到的结果。写结果，不写修改操作清单。

### 范围与约束

明确：

- 范围内包含什么；
- 范围外不包含什么；
- 必须保持成立的兼容性、依赖、平台或运行约束。

### 实现方向

从职责、组件或数据流层面描述选定的变更路径。为实施者提供足够方向，但不编写可以直接誊抄的实现代码。

### 验收标准与验证方式

编写可观察、可证伪的完成条件。为其分配 `AC1`、`AC2`、`AC3` 等稳定标识，使 Tasks 和验证证据可以引用，而无需复制正文。

将每条验收标准、验证方式与预期证据、负责产生证据的阶段放在同一表中维护：

| AC | 验收标准 | 验证方式与预期证据 | 阶段 |
|---|---|---|---|
| AC1 | <可观察、可证伪的完成条件> | <检查方法及预期结果或记录> | 实现期自动化测试 / 系统级验证 / 人工验收 |

使用能以最低可靠成本证明行为的验证层级。不要虚构仓库无法支持的测试层。如果某条标准需要人工判断，写明具体的验收步骤。

## 技术方案（可选）

仅当变更包含实质性决策时写技术方案，例如：

- 引入新依赖、数据模型、API 或模块边界；
- 存在多个具有实质取舍的可行方案；
- 涉及安全、性能、兼容性或迁移影响；
- 决策难以回滚。

记录选定方案、选择理由和主要取舍。如果项目现有模式已经决定实现方式，不强制制造多个备选方案。

### 架构决策记录（按需）

编写或更新计划时，按项目标准识别值得长期追溯的决策：边界、契约、数据归属、可靠性语义，以及有实质取舍或调整成本较高的技术选择。任务排序、普通实现细节和沿用现有模式的改动留在计划中。

- **维护条件**：仅在用户明确要求或有适用的 ADR 维护规则时创建、更新记录，无需重复确认已有授权；目录或历史记录本身不构成授权。无上述依据时，只在计划中记录取舍，不建立文档体系。
- **复用与替代**：已有 ADR 覆盖该决定时直接引用，重复运行不重复建档；实质改变已接受决策时，按项目规则新增替代记录、维护状态与关联，保留旧记录、编号和历史理由。
- **状态与依据**：仅凭明确确认依据标为已接受，实质影响计划的未决选择先澄清；不补造备选方案、理由或确认经过。决策状态与实施、验收状态分开。
- **格式与引用**：路径、编号、格式、状态、替代关系和导航服从项目规则，不强制模板或双向链接。ADR 记录背景、决定、理由与代价，重新评估条件按需；机制与规范留在设计或契约中，计划引用 ADR 组织实施与验证，不重复正文。

## Tasks（可选）

仅当工作包含可独立实现的单元、依赖顺序、并行价值、独立回滚价值，或可能跨会话执行时拆分 Tasks。

Task 是执行切片，不是局部验收契约。每个 Task 包含：

```markdown
### T1：<结果导向的名称>

- 结果：<该 Task 产生的能力或状态>
- 边界：<该 Task 负责的职责或组件；必要时说明不包含什么>
- 依赖：<Task ID；无依赖时省略>
- 覆盖：<验收标准 ID；有助于追踪时填写>
```

结果和边界必填；依赖与覆盖按需填写。边界描述职责或组件范围，不要求列出具体文件。

不要在每个 Task 中重复完整验收标准或测试方式。不要按文件数量限制 Task，也不要把 Task 写成逐行实现指令。

只有当中间状态本身具有独立风险、不可逆、可单独部署，或必须在后续工作开始前得到证明时，才增加局部门槛。局部门槛只写一个可观察条件。

只要拆分了 Tasks，就必须有进度表。优先沿用仓库已有进度表及其格式，并引用其位置；没有时，在正文 Tasks 部分末尾创建仅含 Task、状态的进度表，状态中可简述未验证项或阻碍。进度只在所用表中维护。计划中写明由后续外层执行者在进展或验证结论变化、交接时更新进度与下一步。Task 按其结果、边界和适用门槛判断完成，不等同整体验收通过。

## 输出结构

默认使用以下单文档结构，不适用的可选章节直接省略。有 Tasks 时，开头简述下一步并指向实际使用的进度表；Task 正文保持简短，详细验收内容放在后续章节。仅在用户明确要求或项目已有约定时拆分文件。

```markdown
# Plan：<名称>

## 目标

...

## 范围与约束

- 范围内：
- 范围外：
- 约束：

## 实现方向

...

## 技术方案

...

## Tasks

...

### 进度

<仓库已有进度表时仅引用其位置，否则使用下表>

| Task | 状态 |
|---|---|
| T1 | <实际状态；必要时简述未验证项或阻碍> |

## 验收标准与验证方式

| AC | 验收标准 | 验证方式与预期证据 | 阶段 |
|---|---|---|---|
| AC1 | ... | ... | 实现期自动化测试 / 系统级验证 / 人工验收 |
```

范围明确且在同一会话内完成的计划保留在对话中。用户要求写入文件，或多个 Tasks、会话、agents 之间需要持久交接时，再保存计划。用户指定路径时使用该路径；不要自行发明文档拓扑。

## 自检

结束前确认：

1. 目标和边界已经明确到足以进入实现；
2. 实现方向符合仓库约束；
3. 每条验收标准都有对应的测试或验收方式；
4. 可选 Tasks 以结果为导向、边界清晰，并共同覆盖计划范围；
5. 不存在会实质改变计划的未解决选择；
6. 相关 ADR 已按维护条件复用或更新，计划引用有效，决策状态有依据且历史得到保留；不适用时未额外创建记录；
7. 没有修改生产代码、测试代码或无关项目文件。

展示或保存计划并完成适用的 ADR 维护后，本 skill 的职责到此结束，不自动启动或要求后续流程。用户已授权复合任务时，外层执行者继续剩余工作；用户仅要求本阶段时，交付结果后结束任务。

## 边界

以下限制适用于本 skill 的规划职责，不限制外层执行者继续用户已授权的其他阶段。

不要：

- 修改生产代码或测试；
- 创建 worktree、commit、push 或 Pull Request；
- 开始代码实现、执行代码审查或系统验证；
- 强制拆分 Tasks、提供多个技术备选或要求额外的计划审查；
- 在每个 Task 中重复验收标准或验证说明。
