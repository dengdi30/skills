# 独立代码审查

使用上下文干净的 fresh subagent，对明确的候选变更进行只读、证据驱动的审查，帮助用户判断哪些问题值得修复。

默认从需求符合性、正确性与回归两个角度检查，分别呈现意见，不签发 `APPROVE / BLOCK` 或要求 findings 清零。是否修复、接受风险或再次审查由用户决定。

本 skill 可以独立使用，不要求需求文档、Plan、实现报告或测试证据存在，不依赖其他 skills，也不自动发起后续流程。

## 审查目标

支持当前工作区变更、staged changes、单个 commit、commit range、branch diff、Pull Request，以及用户直接提供的 patch 或 diff。

用户只说“审查当前修改”时，默认审查完整工作区候选，包括 staged、unstaged，以及属于本次变更的 untracked 文件。

如果无法区分本次变更与无关工作区修改，或审查范围存在会实质改变结论的歧义，先请求最小澄清。

## 可选上下文

存在时使用以下信息增强审查，不存在时仍完成代码审查：

- 用户需求、issue 或 spec；
- Plan 中的需求、范围、约束与验收标准，以及适用的合同或架构决策；
- 技术和兼容性约束；
- 测试命令与结果；
- CI 报告；
- candidate SHA 或 diff hash；
- 用户请求修复复查时的前次候选、审查记录和修复差异。

材料可以来自用户、issue、spec 或计划文档，不要求由特定 skill 生成。先查找当前任务已有材料；没有可用需求依据时，将需求符合性标为“未检查：缺少需求依据”，继续正确性与回归检查，不从实现反推需求。

只传递客观材料。不要把实现者的推理过程、辩护、预期结论或主会话未经核验的怀疑传给 reviewer。前次 findings 是待核验的审查记录，不是已成立的结论。

## 候选快照

审查前确定：

```text
base revision
candidate 标识
changed files
完整 diff
```

candidate 标识可以是 commit SHA、base/head SHA、PR head、diff hash 或等价稳定标识。

完整 diff 必须覆盖审查范围内的生产代码、测试、配置、迁移和新增文件，不能只包含可见的 diff hunks 或默认 `git diff` 输出。

所有 reviewer 必须检查同一 candidate。汇总前确认候选未变；审查期间候选发生变化时，报告变化并停止，不把旧快照的意见作为当前候选的审查结果。

## 审查分工与上下文隔离

复杂变更且两个角度均适用时，分别创建不继承当前对话的 fresh subagent 并行检查。简单变更可由一个 fresh reviewer 覆盖两个角度；只有一个角度适用时只安排该角度。不要为了凑齐维度增加 reviewer。

传给每个 reviewer 的内容仅包括：

- 审查目标、分配的角度及本 skill 中适用的规则；
- candidate 信息；
- 完整 diff 和 changed files；
- 可选需求与验收标准；
- 可选客观测试证据；
- 必要的仓库级约束；
- 修复复查需要的前次客观记录。

并行 reviewer 不接收彼此的推理或发现，也不再委派其他 reviewer。各自先按下述规则自我核验，再返回 findings、已检查范围及重要缺口，由主会话核对并汇总。

每个 reviewer 在现有报告中附简短检查记录，注明 reviewer 标识、审查角度、base/candidate 及输入材料引用；共用信息可引用主会话的候选快照。记录按相关路径或验收项合并，包含“检查范围或要求、核验方式与结果、证据位置及来源”；已检查但未发现问题的范围也要给出依据，无需逐文件、逐命令记流水账。

优先引用运行环境已有的可定位工具轨迹，区分原始工具记录、代码依据与 reviewer 自述。无法取得执行记录时，提供可复核的代码依据或检查摘要，并注明对应执行过程未独立确认；不得虚构日志、步骤或实验结果。记录可随 reviewer 报告返回，不要求新增日志系统或文件产物。

Reviewer 可以只读检查相关源码、调用方、类型、配置和仓库既有模式；根据具体风险沿调用链检查业务流程与受影响边界，不应被限制为只看 diff hunks，也不默认扩大为全仓库审计。

如果运行环境不支持 fresh subagent，明确说明无法保证上下文独立。只有用户接受时，才进行同上下文的降级审查。

## 两个审查角度

### 需求符合性

检查当前有效的需求、范围、约束与验收标准是否得到实现，指出遗漏、部分实现、误解和未经要求的行为。存在稳定的验收标准编号时直接引用，并给出原文依据和实现证据。

明确要求和已确定的技术约束是审查依据；可选方案或实现建议不能仅因未被采用而形成 finding。用户最新明确要求优先于旧文档，发现冲突时说明依据，不机械执行过期计划，也不擅自改变需求。

验收标准需要系统级验证或人工判断时，只报告可从代码和已有证据确认的部分，其余列为缺口；不因本轮未执行这些阶段就判定实现不符合要求。

### 正确性与回归

检查实现在具体条件下是否出错，以及变更对已有行为的影响，按相关性检查：

- 业务流程的可达性、状态转换，以及失败、取消和重试后的恢复；
- 数据写入、事务、并发、幂等和副作用的一致性；
- 安全、权限、敏感数据，以及有实际影响的性能问题；
- 调用方、接口语义、数据格式和错误传播的兼容性；
- 事务边界、权限边界、资源所有权或依赖关系变化造成的具体后果。

业务流程和架构问题必须落到失败条件及现实影响，不单独输出架构偏好、推测性重构或“更优雅”的设计建议。

### 两个角度共用的检查方法

测试质量融入上述角度，不另设测试审查栏目。检查测试是否能捕获相关需求偏差或行为错误，特别关注：负例是否被无关错误提前拒绝，预期结果是否复制实现假设，移除目标校验或副作用后测试是否仍可能通过。区分代码推导和实际运行证据。

发现具体反例后，提取被违反的规则，检查受影响范围内的同类路径、状态和记录类型。完整性检查既要检查已有记录是否合法，也要根据实际执行路径判断必需记录是否存在，包括整组缺失；保留合法未产生或未调用路径。按相关性展开，不强制建立矩阵或机械执行变异测试。

不要报告纯个人编码偏好、formatter 或 linter 可处理的样式问题、与候选无关的历史问题，以及没有具体失败场景的理论风险。未检查或证据不足应列为缺口，不自动转成缺陷；没有有据可查的问题时可以没有 finding。

## 输出前自我核验

每个 reviewer 在提交发现前，主动尝试推翻自己的判断，不把第一印象或其他 reviewer 的结论当作事实。逐条核验拟报告的问题：

1. **依据有效**：引用的是当前有效的要求或行为契约，未把可选方案、个人偏好或过期文档当作要求。
2. **场景可达**：沿必要的调用链确认触发条件在实际使用中成立；检查上游校验、分支条件、异常处理、事务或补偿机制是否已经排除该问题。
3. **证据支持结论**：在同一 candidate 上确认从触发条件到错误行为、再到实际影响的因果链。声称是回归时对照基线；测试失败时确认失败来自目标条件，而非环境、输入构造或其他错误。
4. **排除合理反证**：检查相关上下文和已有测试是否否定判断。静态证据足够时不必运行测试；存在关键疑点且可低成本验证时，按命令边界做定向检查，未运行的实验不得写成结果。

核验成立的才作为 finding；被反证推翻的直接删除；仍缺关键事实、且会影响用户判断的内容放入对应栏目的“待确认 / 检查缺口”，说明缺什么证据，不计入问题数量。不要把所有初步猜测都交给用户筛选。

在 finding 的证据中关联检查记录，简述核验方式、关键反证核验及支持结论的事实，区分代码推导与已执行的检查，不输出完整思考过程。主会话核对这些证据与引用，遇到缺口或矛盾时返回材料核查，不仅转述 reviewer 的结论；无需为此额外启动一轮完整审查。事实是否成立由审查者先核验，是否修复再由用户决定。

主会话核对检查记录与候选、来源和引用是否一致，对审查步骤的执行情况按可见证据区分“已确认执行”“已确认偏离”和“证据不足”。没有可见日志不等于没有执行；代码依据支持事实判断，工具记录支持操作发生，均不能单独证明审查充分或全部指令已落实。主会话补充复现须单独标明来源，不作为 reviewer 已执行相同步骤的证明。

## Findings 与汇总

每条 finding 必须有位置、具体失败场景、证据和实际影响。严重程度仅描述影响，不决定用户是否必须修复：

- **严重**：核心需求或流程失效、安全漏洞、数据丢失或破坏、重要兼容性回归等重大后果。
- **一般**：影响较局部、有实际后果但严重程度较低的问题。

按实际后果判断，测试问题的严重程度取决于它让什么错误逃过检查，不按维度或问题数量定级。

主会话在交付前核对引用与事实，整理方式如下：

- 保留“需求符合性”和“正确性与回归”两个栏目，不合成整体通过结论，不做跨维度总排名。
- 每栏按实际影响排序。同一机制的多个已证实反例合为一条，说明已证实范围，不把未经验证的相邻风险写成事实。
- 同一问题跨维度出现时，完整描述放在依据最直接的栏目，另一栏引用相同 ID；避免重复修复建议和重复计数。仅症状相似但机制不同的问题分别保留。
- Reviewer 判断冲突时先核对代码、需求与证据；不能消除的分歧写明双方依据及待确认点，不以多数票裁决，也不计入已证实问题数。

使用报告内唯一的 `R1`、`R2` 等 ID，格式如下：

```markdown
#### R1 [严重 / 一般] <问题标题>

- 位置：path/to/file.ts:42
- 依据：<需求、约束、验收标准或行为契约>
- 失败场景：<问题在什么条件下发生>
- 证据：<核验方式及关键事实，包括代码位置、已有证据或已执行的定向检查；注明已证实的同类范围>
- 影响：<对用户、数据或系统的后果>
```

## 修复复查（用户请求时）

使用前次候选、客观 findings 和本轮修复差异核验旧问题，沿用其 ID，在对应栏目交代“已解决 / 仍存在 / 无法核验”及依据。发现前次 finding 不成立时明确更正，不要求为错误意见修改代码。

区分原始基线到当前候选的整体变化与前次候选到当前候选的修复变化；优先检查旧问题、同类路径和修复影响，扩展范围时说明具体依据。只有标识但无法取得旧快照或报告时，说明比较限制，不编造修复状态。

新发现仍按证据报告，能确定时说明是此前遗漏还是修复引入，不能确定时标为待确认；不因它在修复差异之外就排除原审查范围内的真实问题。用户要求重新全量审查或候选实质扩围时，按相应范围检查。本轮以交付审查意见结束，不追求固定轮数或问题清零。

## 命令边界

Reviewer 可以读取已有测试证据，也可以为验证具体怀疑运行小范围定向检查；不得修改候选文件、索引或分支状态。需要临时实验文件时仅在隔离临时目录中创建，结束后清理。

Reviewer 不负责运行完整测试套件、建立测试环境或执行系统级验收。命令结果只能支持审查 finding，不能替代独立的动态验证结论。

## 输出

```markdown
## Review

- Candidate：<SHA / diff hash / PR head>
- 范围：<本轮审查范围；修复复查时注明前次候选及比较限制>
- 审查记录：<各 reviewer 的记录引用及执行证据的重要缺口>

### 需求符合性

- 检查情况：<已检查范围及重要缺口；无需求依据时明确未检查>
- <本栏 findings、跨栏引用；复查时附旧问题状态>

### 正确性与回归

- 检查情况：<已检查范围及重要缺口>
- <本栏 findings、跨栏引用；复查时附旧问题状态>

### 汇总

- 需求符合性：<本栏独立问题数>；最重要：<ID 与影响，或无已证实问题 / 未检查>。
- 正确性与回归：<本栏独立问题数>；最重要：<ID 与影响，或无已证实问题 / 未检查>。
```

数量只统计在本栏完整描述、当前仍成立的独立问题；跨栏引用注明所属栏目，不重复计数，已解决项和未决分歧不计入。各栏最重要的问题可以引用另一栏的 ID，但不据此增加数量。

已检查且未发现问题时写“未发现有具体证据支持的问题”；未检查时明确原因，不写成“0 个问题”。数量只用于概览，不代表质量评分，也不承诺审查全面。

## 边界

以下限制适用于本 skill 的审查职责，不限制外层执行者继续用户已授权的其他阶段。

不要：

- 修改生产代码、测试或其他候选文件；
- 修改需求、Plan 或验收标准；
- 自动修复 findings；
- commit、push 或更新 Pull Request；
- 自动调用或要求其他 skill；
- 决定调用者后续的工作流；
- 替用户决定修复取舍、接受风险或签发人工验收结论。

返回绑定 candidate、按两个角度呈现的审查意见。本 skill 的职责到此结束，不自动启动或要求后续流程。用户已授权复合任务时，外层执行者继续剩余工作；用户仅要求本阶段时，交付结果后结束任务。
