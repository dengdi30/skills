# TDD 实现

根据明确的实现目标产出候选实现和必要的持久化测试。

本 skill 只负责实现。它不改写输入需求，不做独立审查，不签发系统级最终验收结论，也不推进合并流程。

## 输入契约

可以接收用户需求、issue、spec、Plan、Task 或其他等价的实现说明，不要求固定格式或来源。

开始前必须能够从输入和仓库上下文确定：

- 要实现的目标行为或结果；
- 范围内、范围外和必须保持的约束；
- 可判断完成的条件。

实现方向、技术方案、Tasks、验收标准和测试方式存在时应当利用，但不是调用本 skill 的前置条件。

如果存在 Tasks，按依赖顺序执行并遵守每个 Task 的边界；同时读取调用者提供的其他上下文，不孤立执行单个 Task。

如果缺少足以实施的信息，请求最少的澄清。如果必须改变目标、范围、完成条件或已明确的技术决策才能继续，停止并报告；不要静默补充或改写输入。

## 实现职责

本 skill 可以修改：

- 生产代码；
- 具有长期回归价值的自动化测试；
- 测试所需的 fixture、helper 或最小测试支撑结构；
- 输入明确要求持久化的集成或 E2E 测试资产。

只实现输入范围内的行为。遵循仓库现有模式，避免无关重构、顺手优化和超出完成条件的功能。

### 持久化集成与 E2E 测试

仅当测试具有长期回归价值时写入仓库，例如稳定的核心用户旅程、低层测试无法覆盖的关键协作，且仓库已有可确定运行的测试基础设施与 fixture。

不要把一次性视觉检查、临时验收流程、不稳定第三方交互，或与已有测试重复且没有额外定位价值的场景沉淀为持久化 E2E 测试。这些场景作为尚待系统边界验证的事项报告给调用者。

本 skill 新增或修改的自动化测试必须至少运行一次。集成或 E2E 测试只需运行新增或直接相关的范围，不要求在实现阶段重复执行完整套件。未执行的测试代码不能作为有效实现产物。

## Test-first 判定

对一个行为切片严格执行 test-first，仅当以下条件同时成立：

1. 变更引入或修复可观察行为；
2. 实现前存在稳定、合理的测试支点；
3. 测试能够让真实可能出现的错误实现失败；
4. 测试验证行为契约，而不是内部实现；
5. 测试的长期回归价值高于维护成本。

判断针对行为切片，而不是整个实现目标或整个 Task。一个 Task 可以同时包含不同实施模式。

在存在可靠测试支点时，以下行为默认严格 test-first：

- Bug 的稳定复现与回归；
- 业务规则、公开 API、协议或数据契约；
- 权限、认证和安全边界；
- 金额、计费、配额和关键计算；
- 数据完整性、状态机和状态迁移；
- 并发、幂等、重试和去重；
- 边界条件较多或回归代价较高的核心行为。

高风险本身不等于必须写低层测试。如果缺少可靠测试支点，应在合适的系统边界提供证据，而不是通过大量 mock 制造形式上的 test-first。

## 实施模式

### 模式 A：Test-first

适用于满足 test-first 判定的行为：

1. 选择一个最小行为切片及其预期行为或完成条件。
2. 编写一个能区分正确与错误实现的最小测试。
3. 运行测试，确认它因目标行为尚未实现而失败。
4. 编写使测试通过的最小生产代码。
5. 重新运行测试，确认通过。
6. 必要时重构，并保持相关测试通过。

测试若因语法错误、环境问题或错误断言失败，不算有效 RED。先修正测试，再开始实现。

### 模式 B：Characterization-first

适用于行为保持型重构：

1. 确认现有测试已经保护目标行为。
2. 覆盖不足时，补充能刻画现有行为的 characterization tests。
3. 完成重构。
4. 运行相关测试，确认外部行为未改变。

Characterization test 可以从一开始就是 GREEN；不要为了制造 RED 而写错误断言或暂时破坏代码。

### 模式 C：Verification-backed implementation

适用于机械变更、静态约束，或主要只能在系统边界证明的行为，例如视觉布局、浏览器流程、跨服务集成和环境配置。

1. 完成输入范围内的最小实现。
2. 运行适用的编译、类型检查和相关已有测试。
3. 仅当新测试具有明确长期价值时增加持久化测试。
4. 系统边界的最终验证结论不属于本 skill。本 skill 可以运行新增或相关的集成、E2E 或 Playwright 测试并交付证据；调用者可以复用绑定最终 candidate 的充分证据，或按自身流程补跑缺失、失效及需要独立环境的验证。

如果必须先建立测试支点，可以先做不包含目标行为的最小结构调整；支点形成后，在实现目标行为前回到模式 A。

## 测试价值检查

新增测试前确认：

- 错误实现时它会失败；
- 它断言可观察行为，而非私有方法或内部调用顺序；
- 内部重构后它仍然成立；
- 它没有重复编译器、类型系统或现有测试已经完整保证的内容；
- 它不依赖与目标行为无关的大量 mock；
- 它能够防止一个真实且有影响的回归。

不要要求每个函数都有测试，不设置统一覆盖率目标，也不要为 trivial getter、框架自身行为、mock 调用次数或纯实现细节编写测试。

## 执行纪律

- 按输入要求和 Task 边界实施，不自行扩大范围。
- 使用仓库已有测试工具和约定，不为单次变更引入新的测试框架。
- 实现过程中运行最相关、反馈最快的测试或静态检查。
- 新增或修改的测试至少执行一次，并保留可供调用者判断是否复用的命令、范围、环境和结果。
- 不要求每个 Task 单独 commit 或运行完整测试套件。
- 发现输入要求与代码现实冲突时，区分局部实现调整和实质性目标、范围或方案变更；只有后者需要停止并请求更新后的要求或决策。
- 不因为局部测试通过就声称完整需求已经验收。

## 完成条件

结束前确认：

1. 输入范围内的实现已经完成；
2. 调用者提供的 Tasks（如有）的结果、边界和依赖得到遵守；
3. 高价值且适合的行为完成了有效 test-first；
4. 新增测试具有明确回归价值；
5. 新增或修改的测试至少执行过一次，相关快速测试、编译或类型检查已经通过；
6. 没有静默偏离输入要求。

完成后简要报告：

- 已实现的需求、目标行为或完成条件；
- 使用过的实施模式及原因；
- candidate 标识（commit SHA、diff hash 或外层工作流提供的等价标识）；
- 测试命令、执行范围、环境、结果及其覆盖的目标行为或完成条件；
- trace、截图或测试报告路径（如有），以及测试运行后 candidate 是否变化；
- 尚待系统边界验证的事项。

然后停止并将候选实现与证据返回调用者，不能由本 skill 自行批准。

## 边界

不要：

- 修改或补写调用者提供的需求、spec、Plan 或 Task；
- 为满足 TDD 仪式编写低价值测试；
- 因本 skill 自己运行的测试通过就签发最终验证结论；
- 执行独立代码审查或系统级最终验收；
- 创建 worktree、commit、push、Pull Request 或 merge；
- 宣称完整需求已经通过最终验收。
