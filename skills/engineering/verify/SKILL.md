# 动态验证

针对确定的验证对象和预期，使用最小但充分、可信且可审计的动态证据判断结果是否符合预期。

本 skill 可以独立使用。它不要求固定文档、实现报告或测试证据存在，也不依赖其他 skills 或自动发起后续流程。

## 最小输入

有效验证至少需要：

1. **验证对象**：工作区、commit、branch、PR、build、应用、URL、API、服务或部署环境。
2. **预期**：用户描述、issue、spec、验收标准、现有行为契约、测试套件或明确的系统不变量。

不要求输入具有固定格式或来源。

没有明确预期时，可以报告现有测试是否通过或系统是否健康，但不能声称结果“符合预期”。只有缺少的信息会阻止形成结论时，才请求最小澄清。

## 目标绑定

开始前记录能够唯一识别验证对象的信息，例如：

- candidate SHA、diff hash 或 PR head；
- build ID 或 artifact digest；
- deployment version；
- URL、环境和服务版本；
- 其他等价稳定标识。

所有证据和结论必须绑定该目标。目标发生变化后，旧证据不能自动证明新目标。

## 验证原则

测试是证据，不是目标。使用能以最低可靠成本证明预期的验证层级，不默认运行所有可用检查。

可使用：

- build、编译和类型检查；
- 单元、组件和契约测试；
- API、数据库和跨服务集成测试；
- E2E、Playwright 和 smoke test；
- 性能或安全检查；
- 截图、trace、video、console 和 network evidence；
- 无法可靠自动化时的明确人工验收步骤。

对每条预期建立证据映射：

```markdown
| 预期 | 验证方式 | 证据 | 状态 |
|---|---|---|---|
| 用户可以完成登录 | Playwright 用户旅程 | trace.zip | PASS |
| 错误密码不创建 session | API 集成测试 | command output | PASS |
```

不能只因为测试套件绿色就声称所有预期成立。确认测试实际执行目标行为并包含有效断言。

## 证据复用

已有证据满足以下条件时可以复用：

- 绑定当前验证对象；
- 运行后目标没有变化；
- 环境能够代表当前验收目标；
- 执行范围覆盖对应预期；
- 输出完整，包含退出状态和必要 artifacts；
- 没有已知 flaky 问题；
- 不存在必须由独立环境重新执行的信任边界。

不要为了流程完整机械重跑充分证据。

出现以下情况时补跑：

- 目标或环境变化；
- 覆盖不足；
- 日志或 artifacts 不完整；
- 测试没有真正断言目标行为；
- 测试存在 flaky；
- 必须在 CI、容器或真实依赖环境执行；
- 用户明确要求 fresh run。

## Web 验证

仅在验证 Web 应用时读取 [Web 验证细则](references/web-verification.md)，选择工具、准备服务并执行浏览器验收。非 Web 验证无需读取该资源。

## 缺少验证基础设施

所需基础设施不存在时：

1. 判断是否可以用更低层但充分的证据验证。
2. 尝试不修改候选的一次性验证，例如临时脚本、直接 API 调用或可用浏览器能力。
3. 需要安装工具、下载浏览器、外部写入或产生明显副作用时先获得授权。
4. 仍无法获得充分证据时，将对应预期标记为 `BLOCKED`。
5. 按“结果状态”汇总必需项；已有 `FAIL` 时，其他项的 `BLOCKED` 不改变整体失败结论。

不要自行向项目添加持久化测试框架、配置、依赖或测试目录。

## 只读与临时产物

以下限制适用于本 skill 的验证职责，不限制外层执行者继续用户已授权的其他阶段。

可以：

- 运行已有测试和应用；
- 启动必要的本地服务；
- 在临时目录创建一次性验证脚本；
- 创建隔离测试数据；
- 收集日志、截图、snapshot、trace、video 和报告；
- 检查已有证据是否充分。

不要：

- 修改生产代码或持久化测试；
- 调整预期来迎合当前行为；
- 为了通过验证而修复候选；
- commit、push 或更新 Pull Request；
- 自动调用或要求其他 skill；
- 决定调用者后续工作流。

如果发现值得长期保留的测试缺口，只报告为回归测试候选，不修改仓库。

## 环境与副作用

执行集成、E2E 或 smoke 验证前确认：

- 目标环境；
- 测试账号与数据隔离；
- 是否会发送消息、扣款、调用第三方或修改真实数据；
- 是否具有授权；
- 是否可以清理或回滚。

优先使用本地、测试或 staging 环境。使用幂等数据，记录创建的资源，并在验证后清理。无法保证安全时停止，将对应项标记为 `BLOCKED`。

## 结果状态

每条预期使用四态：

- `PASS`：证据充分支持预期成立。
- `FAIL`：证据明确证明行为不符合预期，包括候选实现导致的启动或就绪失败。
- `BLOCKED`：环境、权限、依赖或基础设施阻止验证。原因未确定且无法继续验证时，记录阻碍与不确定性，不推断候选通过或排除候选缺陷；已有证据证明候选缺陷时使用 `FAIL`。
- `NOT_RUN`：超出授权、需要人工判断或被明确排除，因此未执行。

整体结论仅汇总必需项，按以下顺序判定：

1. 至少一个必需项为 `FAIL`，整体为 `FAIL`。
2. 否则，至少一个必需项为 `BLOCKED` 或 `NOT_RUN`，整体为 `INCONCLUSIVE`。
3. 否则，所有必需项均为 `PASS`，整体为 `PASS`。

不能把 `BLOCKED`、`NOT_RUN` 或“测试没有运行起来”当作 `PASS`。

## Flaky 与重试

只在怀疑瞬时环境问题时做有限重试，并保留首次失败和后续结果。结果不稳定时标记 flaky；flaky 不能视为可靠 `PASS`。

不要无限重试直到绿色，也不要用重试掩盖可复现失败。

## 回归测试候选

验证结束后，判断本次场景是否值得转化为持久回归测试。考虑：

- 未来回归概率与影响；
- 是否已有等价覆盖；
- 测试是否稳定；
- 长期运行与维护成本；
- 能否在更低测试层级捕获同一问题。

只报告真正值得考虑的候选，不自动创建测试。即使本次通过 E2E 验证，持久化时也优先建议能够捕获同一回归的最低可靠测试层级。

缺少持久回归测试不影响当前 `PASS`，除非预期明确要求必须增加该测试。

## 输出

```markdown
## Verification

- Target：<candidate / build / environment>
- Expected source：<用户描述 / issue / spec / 现有契约>
- Verdict：PASS / FAIL / INCONCLUSIVE

### Results

| 预期 | 方法 | 状态 | 证据 |
|---|---|---|---|
| ... | ... | PASS | ... |

### Commands

- `<command>` → exit 0

### Artifacts

- screenshots/...
- traces/...
- reports/...

### Gaps

- BLOCKED：
- NOT_RUN：
- 未覆盖的预期：

### 回归测试候选

- 场景：
- 是否建议持久化：
- 原因：
- 推荐测试层级：
```

结论必须绑定验证对象，并明确区分行为失败与无法验证。本 skill 的职责到此结束，不自动启动或要求后续流程。用户已授权复合任务时，外层执行者继续剩余工作；用户仅要求本阶段时，交付结果后结束任务。
